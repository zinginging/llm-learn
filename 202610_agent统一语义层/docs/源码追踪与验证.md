## 2 Cube：服务、模型编译和加速连在一起

### 从请求到 SQL

主要入口是 `packages/cubejs-api-gateway/src/gateway.ts`。网关负责规范化查询、检查 API scope、调用编译层并交给执行层。`CompilerApi` 管理模型编译和 SQL 获取；`PrepareCompiler`、`CubeEvaluator`、`JoinGraph` 组织模型与关系。

[gateway.ts:1486](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-api-gateway/src/gateway.ts#L1486) 的顺序是：求值成员表达式 → `applyRowLevelSecurity` → 用户配置的 `queryRewrite` → 再处理新增表达式。因此自定义重写属于可信服务端代码，部署验收必须检查它是否保留权限过滤。

SQL 生成不能只理解为 TypeScript/JavaScript 实现。当前 [BaseQuery.js:1056](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-schema-compiler/src/adapter/BaseQuery.js#L1056) 会在相应配置路径调用 `nativeBuildSqlAndParams`；[PreAggregations.ts:981](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-schema-compiler/src/adapter/PreAggregations.ts#L981) 区分原生规划器与旧匹配路径。定位问题时应记录实际启用的规划器。

### 为什么可以处理一对多度量重复

[JoinGraph.ts:125](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-schema-compiler/src/compiler/JoinGraph.ts#L125) 会检查参与相关度量聚合的模型主键；关系树还保存 `multiplicationFactor`。这证明模型编译会考虑关联带来的行倍增。

[BaseQuery.js:1373](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-schema-compiler/src/adapter/BaseQuery.js#L1373) 把普通、被倍增、累计、多阶段成员分开处理；部分分支按模型分别聚合，再组合结果。它不是简单将所有表 JOIN 后做一次 SUM。

**边界：** 主键和关系是建模契约，不能替代实际数据唯一性检查；手写 SQL、错误主键、非加性指标和复杂过滤仍需黄金数据验收。本次未运行 Cube 编译和数据库测试，不据此宣称所有 fanout 都会修复。

### 缓存到底缓存什么

预聚合匹配与查询结果缓存是不同机制。上述 `findPreAggregationForQuery` 选择可用预聚合；旧路径会按候选声明顺序寻找匹配，不能直接称为全局最优成本选择器。

[QueryCache.ts:481](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-query-orchestrator/src/orchestrator/QueryCache.ts#L481) 的静态 key 包含 SQL、参数、预聚合 load SQL，可追加 invalidate。**这段函数没有直接放入原始 securityContext**；权限隔离必须结合权限如何进入最终 SQL/参数、数据源路由与 orchestrator 命名空间验证，不能因为配置 JWT 就宣布缓存天然隔离。

[CompilerApi.ts:530](https://github.com/cube-js/cube/blob/91dfc3b1bf761e87f2914598a68e49801ec6c63a/packages/cubejs-server-core/src/core/CompilerApi.ts#L530) 有真实行级权限改写；未启用 RBAC 时直接返回原查询。成员授权、掩码和多组策略还有进一步组合逻辑。启用开关、组映射和策略内容都是部署配置。

**适配推断：** 多应用共享稳定指标、嵌入式分析、需要低延迟和预聚合运营时，Cube 的服务链路最直接。代价是服务、刷新、存储、身份及缓存隔离运营。

## 3 MetricFlow：把指标请求编译成可执行计划

### 不只是生成一段 SQL

[metricflow_engine.py:522](https://github.com/dbt-labs/metricflow/blob/fe4b8c1ccb72a8ca77494b345777eff20a714119/metricflow/engine/metricflow_engine.py#L522) 的 `query()` 创建执行计划，再由 executor 执行，并返回 query_spec、dataflow_plan、SQL 和结果。`explain()` 复用规划路径，不执行数据库请求。

规划链路可按以下顺序阅读：

1. `MetricFlowQueryRequest` → query parser 与查询验证。
2. 指标求值规划和 `DataflowPlanBuilder.build_plan` → 数据流节点。
3. `DataflowToSqlPlanConverter` → SQL 计划与优化。
4. 数据库 renderer → SQL；SqlClient/executor → 执行结果。

[metricflow_engine.py:637](https://github.com/dbt-labs/metricflow/blob/fe4b8c1ccb72a8ca77494b345777eff20a714119/metricflow/engine/metricflow_engine.py#L637) 检查多输出节点，`query()` 也检查多任务并抛出 `NotImplementedError`。这是当前路径的明确边界，不能把“支持多种仓库 adapter”推导为任意跨库联邦执行。

### entity 的价值：约束合法关联

[semantic_model_join_evaluator.py:55](https://github.com/dbt-labs/metricflow/blob/fe4b8c1ccb72a8ca77494b345777eff20a714119/metricflow_semantics/model/semantics/semantic_model_join_evaluator.py#L55) 明确列出合法与非法 entity 组合：foreign→primary/unique 在合法集合；primary→foreign、foreign→foreign 在非法集合；natural→natural 也被拒绝。Natural 还有 validity dimensions 的检查，不能省略其时间有效性条件。

[dataflow_join_validator.py:43](https://github.com/dbt-labs/metricflow/blob/fe4b8c1ccb72a8ca77494b345777eff20a714119/metricflow/validation/dataflow_join_validator.py#L43) 对“右侧已聚合到 entity 粒度”有专门路径：满足对应条件时无需再次检查 fanout。这说明它同时考虑模型级关联与中间结果粒度。

**与 Cube 的区别：** MetricFlow 更突出依据 entity 类型限制路径，并围绕指标输入构造聚合计划；Cube 的追踪路径更突出关系倍增分析、度量拆分和服务加速。二者都依赖正确模型，不能概括为“一个只拒绝、一个全部修复”。

### 时间和指标是一等规划对象

[dataflow_to_sql.py:32](https://github.com/dbt-labs/metricflow/blob/fe4b8c1ccb72a8ca77494b345777eff20a714119/metricflow/plan_conversion/to_sql_plan/dataflow_to_sql.py#L32) 构造标准和自定义粒度的 time spine sources；数据流 builder 包含累计、offset、conversion 和 JoinToTimeSpine 节点。时间补齐与累计计算属于编译计划的一部分，不是交给 Agent 临时猜测。

**边界：** 本次没有安装 MetricFlow Hatch 环境、运行编译测试或连接 dbt 仓库。代码路径与 entity 规则是静态证据；实际支持维度、生成 SQL 和性能仍待 PoC。HTTP 服务、身份到租户的映射、查询预算、API 稳定性需要集成层负责。

**适配推断：** 已有 dbt、需要统一指标与时间口径的团队最容易复用资产；以任意探索 SQL 或现成 ChatBI 产品为主要需求时，还需额外工具层。

## 4 WrenAI：上下文资产与语义 SQL 展开

### 当前实现与旧教程

当前 checkout 的项目指南将旧 `wren-ui`、`wren-ai-service` 与部署目录指向 `legacy/v1`、`v1-final`。本次分析的是当前 Open Context Engine 路径。Rust workspace 的 [Cargo.toml:17](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren-core/Cargo.toml#L17) 声明 DataFusion 55.1；连接器目录是原生驱动实现。不能沿用旧版 Ibis 或 Docker ChatBI 架构描述当前源码。

### 两道 SQL 检查和延迟连接

[engine.py:177](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren/src/wren/engine.py#L177) 的 `_plan()`：

1. 用目标方言解析用户 SQL，读取 MDL 中模型和视图名。
2. 调用 `validate_sql_policy`，检查语句与配置策略。
3. 抽取被引用模型的子 manifest；创建或复用 SessionContext。
4. `CTERewriter.rewrite()` 展开语义对象并输出目标方言 SQL。
5. `validate_planned_sql` 再检查展开后的语句，防止 MDL view/ref_sql 引入写操作。

[engine.py:117](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren/src/wren/engine.py#L117) 的 `query()` 调用 dry_plan 后才取得 connector 并执行，返回 Arrow table；`dry_run()` 调用连接器的验证路径。dry-plan、数据库 dry-run、真正 query 的证据强度不同。

`strict_mode=False` 和空 denied_functions 是默认配置，但**只读语句检查并不受 strict_mode 控制**。strict_mode 主要约束声明对象等访问范围，不能把关闭 strict_mode 等同于允许任意写语句。若解析/模型抽取出错，启用 strict 或 denylist 时明确报错；默认路径允许尝试完整 manifest，后续仍检查规划输出。见 [engine.py:201](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren/src/wren/engine.py#L201)。

### 行列权限确实存在

[provider.rs:34](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren-core/core/src/logical_plan/analyze/access_control/provider.rs#L34) 定义可插拔 `AccessControlProvider`，包括 row_filter、column_access、collect_required_fields；拒绝列在 wildcard 展开中被省略，显式访问会触发权限错误。`WrenAccessControlProvider` 是具体实现，模型分析与生成阶段使用这些决策。

因此应将前一版“未核实完整行级模型”更新为：**已核实源码存在行列控制机制；未验证本次 Rust checkout 的权限回归测试，也未验证生产身份绑定。** Session properties 必须由可信服务端绑定，不可让客户端自行填写 tenant 就当作身份。

### 三种“记忆/缓存”不要混用

| 机制 | 源码对象 | 能解决什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 规划会话复用 | `mdl/__init__.py` 中 maxsize=32 LRU | 按 manifest、函数路径、properties、数据源复用 SessionContext | 结果缓存、预聚合加速 |
| 业务上下文检索 | memory 的 schema_items、知识索引 | 召回结构与业务解释 | 自动保证指标口径正确 |
| NL-SQL 历史 | `store_query` / `recall_queries` | 复用问法和 SQL 示例 | 写入即代表执行成功或人工确认 |

[store.py:381](https://github.com/Canner/WrenAI/blob/13e8bd3654534c528715e0bb6fa687caca25ebd4/core/wren/src/wren/memory/store.py#L381) 的 `store_query` 接收 NL 与 SQL 并写入索引；函数本身不是数据库成功验证器。“只收录确认过的查询”应由上层流程落实。本次没有安装 memory extra 或测试向量召回。

### 实跑：声明模型不会自动纠正手写错误粒度

[黄金案例脚本](../scripts/wren_golden_case.py) 使用当前 checkout 的 Python Wren、锁定的 `wren-core-py 0.8.0` 发布 wheel、DuckDB 1.5.0、sqlglot 29.0.1。创建三张小表并通过 WrenEngine.query 真正执行，不调用外部数据库。

| SQL 路径 | tenant A 净收入（分） | tenant B（分） | 全部（分） |
| --- | ---: | ---: | ---: |
| 退款先按订单聚合，再与订单关联 | 27000 | 25000 | 52000 |
| 订单直接 JOIN 退款明细与商品明细 | 54000 | 50000 | 104000 |

strict 模式拒绝未声明表，断言通过。这里没有定义关系计算字段或专用聚合对象，只在声明基础模型上执行两种手写 SQL；结果证明这条路径保留了错误关联 SQL 的重复计数。**不能把它扩大为 Wren 所有关系规划都无法处理 fanout，也不能把正确 SQL 的租户分组当成行级权限验收。**

**适配推断：** 已有 Agent、需要业务上下文和受控 SQL 工具的团队，Wren 可减少语义模型展开与连接器开发。仍需把确定指标交给稳定模型，维护知识和已确认示例，并验证权限和查询预算。

## 5 Ossie：交换、验证和转换损失

### 校验是分层的

[validate.py:35](https://github.com/apache/ossie/blob/c91b5decf3f4c120640f493bf3532dcd1625f6e4/validation/validate.py#L35) 说明五类检查：JSON Schema、名称唯一性、引用、关系列数量、表达式语法；还有 ontology 名称、继承、QName 等检查。加载 YAML 时会拒绝重复显式 mapping key。

[validate.py:361](https://github.com/apache/ossie/blob/c91b5decf3f4c120640f493bf3532dcd1625f6e4/validation/validate.py#L361) 在缺少 sqlglot 或遇到 skip 方言时返回，不验证表达式语法；DAX、MDX、TABLEAU 等在 skip 集合。`OSSIE_SQL_2026` 映射到 sqlglot 默认解析器，这不能证明全部规范函数语义或目标引擎行为等价。

`ValidationWarning` 是非致命诊断，最终流程区分 warning 和真正 error。因此“validator 退出 0”应理解为启用检查范围内通过，不能代替数据库解析、指标计算或权限验证。

### 转换不是无损保证

[ossie_to_snowflake.py:94](https://github.com/apache/ossie/blob/c91b5decf3f4c120640f493bf3532dcd1625f6e4/converters/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L94) 检查版本必须为 `0.2.0.dev0`，拒绝旧 semantic_model wrapper。转换器会对无法映射的数据类型、方言表达式与扩展字段发 warning；[同文件:525](https://github.com/apache/ossie/blob/c91b5decf3f4c120640f493bf3532dcd1625f6e4/converters/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L525) 专门汇报被丢弃字段。

迁移应保留 warning 清单：是否丢失 label、扩展、业务提示或计算表达式，比“输出 YAML 成功”更重要。本次追踪 Snowflake 路径与 Microsoft 校验边界，未穷尽全部转换器，也没有证明 Cube↔MetricFlow↔Wren 的原生双向转换。

### 有目标引擎验证，但不是通用执行服务

[microsoft/engine.py:20](https://github.com/apache/ossie/blob/c91b5decf3f4c120640f493bf3532dcd1625f6e4/converters/microsoft/src/ossie_microsoft/engine.py#L20) 区分离线 TMSL 结构校验与可选 Fabric/Analysis Services 真引擎验证。后者发布临时模型、刷新编译 DAX、求值并删除，需 workspace 和凭证。这个模块补足特定转换路径的验证，不代表 Ossie 提供统一在线查询引擎。本次没有调用该云端流程。

**适配推断：** 多平台迁移、目录互操作、长期语义资产格式适合评估 Ossie；要落地查询服务仍需消费规范的引擎与运行时。

## 6 基于源码的能力矩阵

| 对比项 | Cube | MetricFlow | WrenAI | Ossie |
| --- | --- | --- | --- | --- |
| 输入契约 | 语义成员查询、服务接口 | 指标、维度、过滤的结构化请求 | MDL 上的 SQL；上下文供 Agent 使用 | 规范化模型文件 |
| 核心中间表示 | 模型/关系图、JS 与原生规划路径 | QuerySpec→DataflowPlan→SqlPlan | MDL→DataFusion 逻辑计划→CTE/方言 SQL | 类型对象、Schema、转换后的目标模型 |

| 时间计算 | 引擎能力配合模型配置 | time spine、累计/offset/conversion 节点 | SQL 与 MDL 配合，需定义口径 | 表达式/元数据携带，消费端实现 |
| 执行职责 | 服务与 orchestrator | SqlClient/executor，可封装服务 | connector，返回 Arrow | 目标引擎负责；部分转换器有可选验证 |
| 加速 | 查询缓存、预聚合、刷新 | 计划优化与部分构建缓存，不据此推定结果缓存服务 | SessionContext LRU，与知识索引不同 | 本次追踪范围无通用查询缓存 |
| 权限证据 | RBAC/RLS、成员授权/掩码实现 | 服务身份和数据库控制另行集成 | 只读、strict、denylist、Rust 行列控制 | 校验不执行查询权限 |
| Agent 工程优势 | 稳定服务与成员目录 | 确定性指标编译 | 上下文资产、SQL 工具、示例检索 | 可移植模型资产 |
