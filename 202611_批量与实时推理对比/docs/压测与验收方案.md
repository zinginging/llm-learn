# 批量与实时推理压测及验收方案

本方案用于后续真实测试，不代表本轮已执行 GPU 或供应商 API。目标是在质量和交付约束相同的前提下判断加速是否有效，分别比较在线服务容量、离线作业效率和每个合格产物成本。

## 1 固定测试条件

记录模型完整 ID/权重 revision、tokenizer/chat template、采样与 reasoning 参数、最大上下文和输出限制；自部署另外记录引擎提交/版本、量化与 KV dtype、GPU 型号数量、互联、驱动、CUDA、依赖、TP/PP/DP/EP、内核和调度设置。

输入需包含长度分布、共享前缀比例、任务类型、会话深度和多模态比例。输出记录实际 token、结束原因和质量，不能将失败截断视为更快的同等答案。

缓存分三组：关闭/冷启动、热前缀、可复用结果。冷启动应包括权重加载、编译、图捕获和预热；稳定态测量则单独计时，不将两种数据混为一个均值。

## 2 测试工作负载

| 测试组 | 目的 | 应记录 |
| --- | --- | --- |
| 短输入短输出 | 调度和网络开销 | TTFT、E2E、连接复用 |
| 长输入短输出 | Prefill 压力 | 输入 tokens、cache hit、TTFT |
| 短输入长输出 | Decode 压力 | ITL/TPOT、输出 tokens、取消 |
| 长短混合 | 干扰与公平性 | 分桶尾延迟、饥饿、抢占 |
| 高共享前缀 | 缓存收益 | 实际复用 tokens、写入成本 |
| 低共享前缀 | 缓存最差情况 | 淘汰、额外显存和开销 |
| 突发/逐步增压 | 容量与过载 | 准入、队列、429、失败率 |
| 超长/异常请求 | 稳定性 | 截断、超时、OOM、重算与重试 |

至少报告输入长度和输出长度的分层结果；只用固定短 prompt 很容易得出不可迁移的结论。

## 3 在线压测

使用明确到达过程：恒定到达率、泊松到达、真实 trace 回放或突发。开放环按预定时间提交，闭环在请求结束后才补发；二者负载定义不同，要分开报告。仅用闭环压测可能在变慢时自动减少到达，掩盖排队与 coordinated omission。

逐步提高请求到达率或 token 到达率，观察满足 SLO 的最大稳定容量。记录客户端实际发送时间与计划时间，确认压测机 CPU、连接池、带宽和分词不是瓶颈。

| 指标 | 推荐口径 |
| --- | --- |
| TTFT | 客户端提交到第一个有效内容 token，另列服务端队列/计算信息 |
| TPOT | 每请求首末输出 token 时间差除以 N-1；N≤1 不适用 |
| ITL | 实际 token 间隔；只能观测 chunk 时明确标为 chunk interval |
| E2E | 提交到完整结束，不仅是最后可见字 |
| P50/P95/P99 | 写明样本与分位数方法，按任务分层 |
| Goodput | 成功且满足声明 SLO 的请求/秒 |
| SLO 达成率 | 合格请求数/全部提交请求数，失败不静默剔除 |
| 输出吞吐 | 完成产物 tokens/明确时间窗；失败生成 tokens 另列 |

系统利用率、tokens/s、平均 TPOT 都不能单独替代交互体验。平均 TPOT 正常也可能有单次长卡顿，因此需要最大 ITL 或 ITL 尾部。

## 4 离线与 Batch API 测试

按稳定任务 ID 和输入哈希提交，保存作业创建、进入执行、完成、下载和解析时刻。总作业时长包括排队与最终收尾；如果另报纯 GPU 时间，应明确分开。

结果不依赖输入顺序，以 ID 对齐。区分整作业校验失败和条目错误，只重试适合重试的失败子集；成功结果幂等落库。取消/过期前已完成的工作可能产生费用，按供应商实际账单核对。

有依赖的任务不能直接放在同一批并假设按行执行；多阶段 Agent 或工具任务需要 DAG/工作流，阶段之间等待和外部工具时间应计入业务完工时间。

## 5 成本与质量

托管服务按实际计费类别、模型与批处理规则汇总：未缓存输入、缓存读取/写入、输出、工具、文件存储或其他费用。有些 API 的 write tokens 是 input 的子集，必须先转换成互不重复的计费类别，避免重复相加。

自部署成本至少计入 GPU 数×租用时长、CPU、存储和网络。必要时单列闲置容量、加载与编译、失败重试及运维成本；满载单价与真实业务低谷成本不同。

```text
每合格产物成本 = 总实际费用 / 满足业务质量及交付要求的产物数
```

分母为零时成本未定义，不能填零。批量折扣和缓存折扣不能自行相乘，是否叠加以具体模型和产品规则为准。

质量方面固定黄金样本和评分规则，检查金额/单位、引用、JSON schema、工具参数、截断与拒答。量化、小模型路由、输出压缩和上下文裁剪均需重新测质量，而不仅比较速度。

## 6 每次只验证一个假设

| 修改 | 对照 | 主要判断 |
| --- | --- | --- |
| 增大 token batch budget | 相同并发与模型 | 吞吐是否增长，TTFT/ITL 是否仍达标 |
| 启用 prefix cache | 相同前缀命中分布 | Prefill 与成本改善，显存/淘汰可接受 |
| 启用 speculative decoding | 同目标模型/策略 | 接受率、草稿与验证开销、质量和负载敏感性 |
| 更低精度 | 同任务与硬件 | 内存、速度与质量共同判断 |
| 增加 TP | 同 GPU 总预算的 DP 候选 | 单请求、goodput 与通信成本 |
| Chunked prefill/P-D 分离 | 同混合 trace | 减少阶段干扰是否超过调度/传输代价 |

性能运行重复多次，记录随机种子、误差范围和异常。不要一次同时更换模型、精度、硬件和 batch 后，将全部收益归因于某一技术。

## 7 本轮教学实验的实际范围

[脚本](../scripts/inference_metrics_demo.py) 的时间戳均为人工设计，每个时间戳严格代表一个 token。P95 使用 nearest-rank；只有 4 条样本，因此 P95 恰好为最大值，不具备生产统计意义。

| 人工配置 | 输出 tokens/s | TTFT P95 | 平均请求 TPOT | 合格请求/秒 |
| --- | ---: | ---: | ---: | ---: |
| 延迟取向样例 | 32.0 | 200ms | 100ms | 8.0 |
| 吞吐取向样例 | 约 47.06 | 280ms | 20ms | 0.0 |

教学 SLO 为 TTFT≤200ms、请求平均 TPOT≤100ms、E2E≤800ms。脚本还验证空分位数、单 token TPOT 不适用、失败请求计入提交数、非单调时间戳拒绝与 512MiB KV 手算。

这不是引擎调度模拟，不声称较大 batch 一定出现这些结果，也不能据此比较 vLLM、厂商 Batch API 或实时 API。[实际输出](../intermediate/验证记录.json)
