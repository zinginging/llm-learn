# 大模型批量推理与实时 API 推理对比调研

批量推理通常用更宽松的完成期限换取高吞吐和低单位成本；实时服务则在首 token、连续输出和完整响应的延迟约束下提供有效吞吐。两者可以使用相同模型和推理引擎，区别主要在服务契约、请求到达、调度与资源策略。

本报告以自回归文本生成 LLM 为主，面向应用开发和推理服务学习者。核验日期为 2026-11-04，结论来自官方文档、系统论文和工程分析。本地仅运行人工数据的指标演算，不宣称实测模型或 GPU 加速效果。

## 1 先分清四种“批量”

| 概念 | 发生位置 | 含义 | 与实时服务的关系 |
| --- | --- | --- | --- |
| 厂商 Batch API | 产品接口 | 提交一组异步任务，稍后获取结果 | 通常面向可等待任务 |
| 本地离线推理 | 作业执行 | 数据集交给模型进程批量处理 | 不必通过 HTTP，也可用连续批处理 |
| 客户端并发请求 | 应用侧 | 同时发送多个独立请求 | 仍可调用普通在线 API |
| 引擎批处理 | 服务端计算 | 将多个序列的计算组合调度 | 在线服务同样大量使用 |

因此，“实时 API 每次只处理一个请求”“批量 API 一定将全部样本放进一个 GPU batch”“异步 await 就是厂商 Batch API”，都是不准确的说法。

这里的实时表示交互延迟敏感的在线服务，不限定某一家名为 Realtime 的语音/音视频产品。普通非流式 API 也属于在线服务；流式输出是呈现与传输方式，不是与 Batch 完全平级的模型算法。

## 2 相同点与不同点

### 2.1 相同点

二者都要处理分词、输入上下文、模型前向计算、生成策略、输出解析和质量验证。使用相同模型、tokenizer、权重、提示模板与解码策略时，目标任务可以相同。

但“目标相同”不保证字节级输出一致：随机采样、硬件精度、量化、内核与批次形状可能造成差异。temperature=0 也不是跨实现的绝对一致性保证，仍需固定版本并做质量回归。

### 2.2 对比矩阵

| 维度 | 离线批量任务 | 在线实时服务 |
| --- | --- | --- |
| 用户目标 | 截止前完成大量任务 | 尽快开始且稳定持续响应 |
| 请求到达 | 已知数据集或周期聚合 | 随机到达、突发、会话依赖 |
| 调度自由度 | 可排序、分片、等待凑批 | 受等待预算与优先级约束 |
| 主要指标 | 总完成时间、完成率、成本、tokens/s | TTFT、ITL、E2E、尾延迟与 goodput |
| 资源策略 | 倾向填满 GPU、弹性调度 | 需预热、容量余量与过载控制 |
| 结果交付 | 文件、对象存储、回调或轮询 | 单次响应、SSE/WebSocket 等流式交付 |
| 故障恢复 | 按任务 ID 重试失败分片 | 请求超时、取消、会话与重试处理 |
| 典型场景 | 标注、抽取、离线评估、知识库加工 | 聊天、代码补全、交互式 Agent |

批量不是天然正确率更高，实时也不是天然低 token 单价；要看同模型任务、服务层级和实际计费。

## 3 推理为什么慢：Prefill 与 Decode

```mermaid
flowchart LR
    A[请求进入] --> Q[排队与调度]
    Q --> P[Prefill 处理输入并建立 KV]
    P --> F[首个输出 token]
    F --> D[Decode 逐步生成后续 token]
    D --> O[完整输出与后处理]
```

Prefill 同时处理输入 token，长 prompt 往往产生较大的矩阵计算。Decode 在单序列上依赖前面已生成内容，通常需要反复读取权重和历史 KV，小 batch 时容易受内存带宽或通信限制。

这只是常见瓶颈：长上下文、模型结构、batch、硬件、MoE 路由和并行方案都会改变实际限制。不能笼统说所有 prefill 都纯计算受限、所有 decode 都纯带宽受限。

批量可在不同请求之间增加并行，提升权重复用和计算效率；并没有消除普通自回归模型同一序列逐步生成的依赖。推测解码是另一条利用草稿与验证减少串行目标模型步骤的路线。

## 4 用正确指标比较速度

### 4.1 单请求与整体系统

记客户端发出请求时刻为 t0，收到首个可用输出 token 为 t1，最后 token 为 tn，请求完整结束为 te，输出 token 数为 N。

```text
TTFT = t1 - t0
E2E  = te - t0
平均 TPOT = (tn - t1) / (N - 1)，仅 N > 1 时定义
第 i 个 token 间隔 ITL_i = t_i - t_(i-1)
整体输出吞吐 = 完成请求的输出 token 总数 / 明确的观测时长
```

客户端 TTFT 包含网络、排队、预处理、prefill、首 token 生成及传输，不是纯 prefill 时间。TPOT 的请求均值也不能代替 ITL 的尾部或最长卡顿；部分系统用结束时间近似最后 token 时间，应说明口径。

观测到的是 SSE chunk 时，一个 chunk 可能有多个 token，也可能只有元数据；不能将 chunk 数直接当 token 数。非流式 API 通常无法直接测客户端 TTFT 和真实 ITL。

### 4.2 Goodput：满足要求的有效吞吐

本报告以请求 goodput 表示：单位时间内，成功且满足指定 TTFT、TPOT/E2E 等条件的请求数。明确条件后，才能判断服务是否有用。

例如人为设定 TTFT≤200ms、平均 TPOT≤100ms、E2E≤800ms，某配置虽然输出 tokens/s 更高，却可能所有请求首 token 都超时，goodput 为零。阈值是教学设定，不是通用生产标准。

压测要同时报告 P50/P95/P99、完成率、SLO 达成率和质量。只挑成功且短的请求算均值，会掩盖失败和长尾。

## 5 两类服务都能采用的加速方法

### 5.1 减少不必要的推理工作

优先减少无价值输出、冗余上下文和重复模型调用；固定抽取任务可用合适的结构化格式。减少实际输出 token 往往能缩短 decode，但把 max_tokens 调小而截断答案不算有效优化。

小模型、蒸馏模型、任务专用模型和分层路由可以降低单位任务成本。路由本身也有开销，且必须评价最终业务质量；换模型后不能声称只是引擎加速。

API 的 reasoning/effort 或任务预算在支持的模型上可能影响延迟和质量，不能假设可见输出字数代表全部计算量。对简单任务，应实测是否需要长推理。

### 5.2 区分三类缓存

| 缓存 | 复用对象 | 直接作用 | 边界 |
| --- | --- | --- | --- |
| 当前序列 KV cache | 已处理 token 的 K/V | 避免每步重算全部历史投影 | 仍需处理注意力与新 token |
| Prefix/Prompt cache | 多请求相同输入前缀 | 减少重复 prefill | 不直接消除后续 decode |
| 结果缓存 | 已完成答案/业务产物 | 命中时可跳过模型 | 需校验身份、时效、参数和模型版本 |

共享前缀有利于 prefix cache，通常将稳定说明与工具定义放在可复用前部，把变量放在后部。具体缓存范围、命中方式和计费因模型与服务不同；监测命中 token、写入开销、延迟和费用，而不是只看到“cache hit”。

前缀缓存省显存或释放计算资源也可能间接改善整体调度，但不能称它直接加速每个新输出 token。语义相近不等于可复用同一 KV 前缀。语义结果缓存还要另评估误命中。

### 5.3 高效内核、编译与 CUDA Graph

FlashAttention 类方法通过 tiling 和减少 HBM 读写优化注意力实现；标准 exact attention 路线不应与近似/稀疏注意力混为一谈，也不意味着所有层计算复杂度都消失。

融合算子、优化 GEMM、编译和 CUDA Graph 可减少计算及 CPU 发射开销。收益依模型、形状和硬件而定；编译与图捕获也增加启动时间和内存占用，因此冷启动与稳定态要分测。

### 5.4 量化与 KV 内存优化

权重量化、激活量化和 KV 量化作用不同。INT8、INT4、FP8 等需要匹配硬件与内核；降低精度不必然加速，反量化开销、计算瓶颈或模型质量退化可能抵消收益。

PagedAttention/分页 KV 主要减少碎片与不必要预留，提升可用并发和内存管理效率。它不等同于 FlashAttention；一个偏 KV 管理与访问，一个偏注意力内核 IO 优化，两者可以配合。

CPU/远端 KV offload 能缓解容量或支持复用，但增加传输，可能变慢。是否有利取决于重算成本、命中率和互联带宽。

### 5.5 并行与部署拓扑

| 手段 | 主要作用 | 不适用的简单推断 |
| --- | --- | --- |
| 数据并行 DP | 多副本承接更多请求 | 不直接加速一条请求 |
| 张量并行 TP | 拆分层内计算和权重 | GPU 翻倍不保证延迟减半 |
| 流水线并行 PP | 将模型层分布到不同设备 | 低负载可能有气泡并增加延迟 |
| Expert Parallel | MoE 专家分布 | 仍受路由、负载与 all-to-all 限制 |
| Prefill/Decode 分离 | 两阶段独立扩缩与调度 | KV 转移成本可能抵消收益 |

单卡可放下模型时，先比较多副本和更大 TP 的有效吞吐与成本；不能一律认为多卡模型并行更好。网络、GPU 拓扑、NUMA、CPU 分词和数据供给也会影响结果。

## 6 批量推理怎样优化

### 6.1 托管 Batch API：主要优化作业效率

把相互独立的请求分成合理作业，保留稳定任务 ID、模型版本和输入哈希；避免逐条上传/加载，把结果按 ID 合并，不依赖返回顺序。文件校验、分片、失败子集重试和幂等落库通常比盲目扩大单作业更实用。

批量接口是异步交付契约，不代表用户可直接设置底层 GPU batch 或模型量化。无法承受等待的任务不应因为折扣就强行走 Batch。

### 6.2 自部署离线：填满算力但控制显存

按模型、LoRA、长度和共享前缀分组；短输入不要被很长输入拖累，超长输出避免成为尾部 straggler。分桶、长度排序和缓存亲和有时冲突，需要按任务分布权衡。

一次加载模型后持续供给数据，用流水线连接读取、CPU 预处理、分词、GPU 推理和落盘。使用按 token 的调度预算，而不只固定请求条数；同样 32 条请求可能有完全不同的显存需求。

静态批次可能因长短序列导致填充或完成槽位浪费；连续批处理在迭代边界移除完成请求、加入新请求。它适用于离线作业，也适用于在线服务。

### 6.3 大作业的操作清单

固定最大上下文和输出预算，先采样估计长度与失败率，再逐步增大 token budget、并发和副本数。监测 OOM、preemption、重算、数据饥饿和输出写入瓶颈。作业级指标使用从提交到全部结果完成的时间，不能只算最忙的 GPU 区间。

## 7 实时 API 怎样优化

### 7.1 API 使用方可以做什么

复用 HTTP 连接、选择合适地域和模型，减少重复查询与串行模型轮次；相互独立的检索或请求可并发，依赖前一步结果的工具调用不能机械并行。

用有界并发和自适应限流遵守 RPM/TPM；429 或服务过载时按错误类型退避，避免重试风暴。客户端 async 只是避免等待阻塞，不会自动增加供应商 GPU 容量。

流式输出能让用户更早看到内容、方便取消，但并不天然减少完整推理耗时。代理缓冲、过小网络包和前端渲染也会影响观测到的 token 节奏。

### 7.2 自部署服务端的调度策略

连续批处理根据迭代更新活跃序列，减少请求级固定批次的等待。在线还需控制凑批窗口、优先级与准入：多等一点可提高资源利用率，但排队会进入 TTFT。

Chunked prefill 将长输入切成块，与 decode 交错，减少长 prefill 对持续生成的阻塞。更小块有利于缩短单次阻塞，但可能增加调度开销或延长长 prompt 的首 token；需要同时测 ITL、TTFT 与吞吐。

vLLM V1 文档说明在适用时默认启用 chunked prefill，max_num_batched_tokens 是其中一个调优维度。不要从旧教程照搬开关、默认值或某台 GPU 的推荐数字；固定引擎版本后压测。

### 7.3 推测解码

让较便宜的草稿模型、n-gram 或专门预测头提出多个 token，由目标模型批量验证，减少目标模型串行步骤。精确 speculative sampling 在相应算法假设下保持目标分布，不意味着不同实现、随机种子和浮点内核逐字一致。

草稿成本、接受率、验证开销、额外显存与当前负载共同决定收益。小 batch、长输出、decode 受限时值得评估；高并发已饱和、草稿接受率低或短输出时可能不划算。普通托管 API 未提供控制项时，使用方不能强行开启底层算法。

### 7.4 Prefill/Decode 分离与容量治理

将两阶段放到不同资源池，分别按输入负载和生成负载扩缩，有机会减少干扰并提高满足 TTFT/TPOT 的服务容量。必须计入 KV 跨 GPU/节点移动、路由、排队和容量碎片。

实际在线优化还包括预热权重与内核、保留空闲容量、取消已断开的请求、限制单请求预算、隔离后台批作业。只把 GPU 利用率推到满，不一定得到较好的交互体验。

## 8 优化手段适用矩阵

| 方法 | 离线批量优先级 | 在线优先级 | 主要风险/代价 | 托管 API 使用方可控性 |
| --- | --- | --- | --- | --- |
| 减少冗余输出与调用 | 高 | 高 | 截断或质量下降 | 较高 |
| 小模型/蒸馏/路由 | 高 | 高 | 准确率和路由开销 | 取决于可选模型 |
| Prefix cache | 共享前缀多时高 | 重复上下文多时高 | 命中、时效与隔离 | 按供应商功能 |
| 结果缓存 | 重复任务高 | 高频重复查询高 | 陈旧和错误命中 | 应用可实现 |
| 分桶与离线重排 | 高 | 受等待预算约束 | 公平性与顺序恢复 | 批任务可部分控制 |
| 连续批处理/分页 KV | 高 | 高 | 显存与调度参数 | 一般由服务方控制 |
| Chunked prefill | 混合长短请求时评估 | 长 prompt 干扰明显时高 | TTFT/ITL 取舍 | 一般不可直接控制 |
| 量化/高效内核 | 高 | 高 | 精度、兼容与启动 | 一般不可直接控制 |
| 推测解码 | 按负载测试 | decode 受限时评估 | 接受率、显存和开销 | 取决于产品暴露 |
| DP/TP/PP/EP | 按容量与模型选择 | 按延迟与容量选择 | 通信、气泡、成本 | 托管一般不可控 |
| P/D 分离 | 未必必要 | 高负载严格 SLO 候选 | KV 传输和运维 | 服务方控制 |
| 有界并发/预热/准入 | 保障稳定完成 | 关键 | 容量余量有成本 | 应用与服务方分别负责 |

这里的优先级是工程建议，不是统一性能排序。

## 10 KV 显存如何估算

对常规存储 K/V 的 Transformer，一个序列的粗略 KV 大小为：

```text
KV_bytes ≈ 2 × L × H_kv × d_head × b × T
```

L 是层数，H_kv 为每层 KV heads，d_head 为 head dimension，b 为每个缓存元素字节数，T 为缓存 token 数；系数 2 表示 K 和 V。

教学配置 L=32、H_kv=8、d_head=128、b=2、T=4096，结果为 536870912 字节，即 512 MiB；8 个无共享的同长度序列约 4 GiB，仅为 KV，不含权重、激活、工作区、分页碎片或图捕获。

T 加倍会使该模型下的 KV 近似加倍；GQA 的 KV heads 与 query heads 不同，不能直接用总 attention heads 代入。MLA、混合注意力、滑动窗口、KV 量化和并行分片需按实际实现估算，公式不普适覆盖所有模型。

## 11 怎么做公平比较

固定模型 ID/权重与 tokenizer、GPU 数量型号、精度、内核/引擎版本、输入输出长度分布、解码参数、质量阈值、缓存状态与到达过程。分开比较两件事：同系统不同调度，或业务目标下不同完整方案。

在线用真实到达率、突发和长短混合压测，逐步增压到 SLO 边界；离线比较整个作业完成时间、成功产物数和总成本。不要用无排队单请求 latency 对比饱和吞吐，或用旧系统论文倍数预测今天的 vLLM。

完整方案见 [压测与验收](../docs/压测与验收方案.md)。对于同样业务目标，最终可比较“每个合格产物的成本”和“是否按时交付”，而不只 tokens/s。

## 12 教学演算与选型路径

[指标脚本](../scripts/inference_metrics_demo.py) 用人工时间戳构造两个配置：一组吞吐较低但满足所有延迟阈值，另一组吞吐较高却首 token 全部超阈值。它说明 goodput 与吞吐不等价，不代表真实 batch 策略必然造成该结果。

离线标注、长周期抽取和大规模评估，可先选 Batch API 或本地离线引擎。聊天、交互式取数与需要逐轮工具结果的 Agent，先选在线服务。单轮工具调用可以批量生成，但完整工具闭环需由外部编排多阶段作业，不能假设 Batch API 自动执行工具。

既有在线问答又有夜间任务时，优先分资源池或优先级，避免后台吞吐挤占交互延迟。初期先减少无效调用与冗余输出，随后验证缓存和并发，再按监测瓶颈选择量化、并行、推测解码或 P/D 分离。
