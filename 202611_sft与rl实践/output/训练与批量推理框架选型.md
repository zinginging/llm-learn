# SFT、RL训练框架与批量推理框架怎样选

核验日期：2026-11-16。以下按官方项目和技术文档区分定位。“常见候选”是工程选型范围，不是使用率或性能排名。链接中的main/latest是动态页面；本次没有安装或压测这些项目的新版本，实际跑过的仍只有本主题固定版本TRL微型demo。

## 1. SFT和RL能用同一个框架吗

可以。底层通常都用PyTorch等自动微分系统，执行forward、loss、backward和optimizer更新；一个上层框架也可能同时提供SFT和RL入口。

但**共享框架不等于训练循环相同**：

```text
SFT：固定示范 → teacher forcing → 交叉熵 → 反向传播 → 更新

在线RL：当前策略采样 → 环境/奖励评分 → 优势及策略目标
         → 反向传播 → 更新 → 同步生成端权重 → 新一轮采样
```

RL还可能涉及参考模型、奖励模型、价值网络、工具环境、多个GPU资源池和异步队列，具体取决于算法。GRPO不需要与PPO相同的学习型critic，并不意味着不需要奖励或训练设施。DPO常是离线偏好优化，不应与在线rollout循环混为一谈。

上一份demo直接体现了复用：[SFT](../scripts/sft_demo.py)使用`TRL.SFTTrainer`，[在线GRPO](../scripts/rl_demo.py)使用`TRL.GRPOTrainer`；都用Transformers模型与PyTorch，但数据和目标不同。

## 2. 先分清技术栈的层次

| 层次 | 主要职责 | 代表 |
| --- | --- | --- |
| 张量与自动微分 | 模型计算、梯度、优化器 | PyTorch |
| 模型与基础训练接口 | 模型加载、tokenizer、Trainer、设备/分布式封装 | Transformers、Accelerate |
| 训练工作流 | 数据格式、SFT/偏好/RL目标、采样与训练组织 | TRL、LlamaFactory、Axolotl、verl、OpenRLHF、NeMo RL |
| 分布式训练底座 | 参数/梯度/优化器分片、模型并行、通信 | FSDP/FSDP2、DeepSpeed、Megatron Core |
| 推理执行 | 高效生成、KV cache、请求调度、支持的量化和并行 | vLLM、SGLang、TensorRT-LLM、LMDeploy |
| 数据与任务编排 | 批量读写、预后处理、分区、GPU actor和恢复 | Ray Data；其它数据平台也可组织任务 |

这些层不是互斥产品。例如TRL可配分布式底座；verl可配训练后端和vLLM/SGLang生成后端。**LoRA/QLoRA是微调方法，不是与TRL或DeepSpeed同层的完整框架。**

## 3. 常见训练候选与适配场景

| 项目 | 能力与定位 | 值得优先评估的情况 |
| --- | --- | --- |
| [Transformers Trainer + Accelerate](https://huggingface.co/docs/transformers/main_classes/trainer) | 基础模型训练与设备/分布式封装；在线RL循环需另行组织 | 自定义任务、基础SFT、掌握训练底层流程 |
| [TRL](https://huggingface.co/docs/trl/index) | SFT、偏好优化、GRPO等后训练工具；适合Python定制 | 学习、实验、自定义奖励；本主题demo已使用 |
| [LlamaFactory](https://github.com/hiyouga/LlamaFactory) | 配置化多模型微调；官方矩阵包含SFT、奖励建模、PPO、DPO等 | 快速跑模型微调，统一数据模板与配置 |
| [Axolotl](https://docs.axolotl.ai/) | 配置化训练、LoRA/QLoRA、分布式与后训练能力，包括GRPO相关路线 | 配置管理、模型适配、需要定制和规模扩展的团队 |
| [Unsloth](https://github.com/unslothai/unsloth) | 支持模型上的训练加速/显存优化，包含微调与RL教程 | 显存有限的微调实验；必须确认支持的模型和配置 |
| [verl](https://github.com/verl-project/verl) | 分布式RL后训练，协调训练引擎、rollout和奖励/环境 | 多卡RL、可验证奖励、多轮Agent训练 |
| [OpenRLHF](https://github.com/OpenRLHF/OpenRLHF) | RLHF/Agentic RL流水线，官方包含SFT、奖励模型与多种RL路线，常见组合为Ray、vLLM和DeepSpeed | 希望组织SFT→RM→RL及分布式训练组件 |
| [NeMo RL](https://github.com/NVIDIA-NeMo/RL) | 可扩展后训练工具，官方提供SFT、DPO、GRPO等单机/多机配方 | 已有NVIDIA训练栈、需要相应模型和集群配方 |

不能把框架机械划为“只能SFT”或“只能RL”。选择要看对应版本、算法实现、模型/硬件组合、数据类型与目标规模；拥有某算法入口不代表所有后端组合都受支持。

### 分布式底座为什么单列

- **[DeepSpeed](https://www.deepspeed.ai/)**：ZeRO、offload等训练内存与分布式能力，也有推理相关组件；在此讨论中主要作为训练底座。
- **FSDP/FSDP2**：PyTorch的完全分片数据并行能力，是训练组件，不是完整RL业务流水线。
- **[Megatron-LM / Megatron Core](https://github.com/NVIDIA/Megatron-LM)**：大规模Transformer与模型并行基础设施，可作为上层训练系统的后端。

这里不是简单三选一的排行榜。需要先看上层框架提供哪些组合，再确认TP/PP/EP、分片、checkpoint与模型支持。例如verl的通用SGLang说明与AMD ROCm支持说明存在不同范围，不能将一种硬件上的支持泛化到所有硬件。

## 4. 常见批量推理引擎

| 项目 | 主要定位 | 批量推理中适合关注什么 |
| --- | --- | --- |
| [vLLM](https://docs.vllm.ai/en/latest/serving/offline_inference/) | 高吞吐推理引擎；提供`LLM.generate`/`chat`离线接口，也可服务化 | 多prompt生成、数据标注/合成、批量评测；是常见的首个基线候选 |
| [SGLang](https://docs.sglang.io/docs/basic_usage/offline_engine_api) | 推理引擎与运行时；有离线Engine API，也可在线服务 | 共享前缀、多轮/结构化任务及RL rollout；收益依工作负载与版本 |
| [TensorRT-LLM](https://nvidia.github.io/TensorRT-LLM/quick-start-guide.html) | NVIDIA平台上的LLM推理优化；提供LLM API和服务入口 | NVIDIA硬件、量化、并行和生产性能调优；按后端与模型核对要求 |
| [LMDeploy](https://github.com/InternLM/lmdeploy) | 压缩、部署和推理工具包，包含TurboMind/PyTorch引擎及离线pipeline | 支持模型上的批量推理、多模态、量化和部署 |
| [Transformers](https://huggingface.co/docs/transformers/main_classes/text_generation) | 通用模型加载与`generate`等接口 | 小规模实验、自定义模型、正确性基线；吞吐需与专用引擎实测比较 |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | C/C++推理，支持GGUF和多种硬件后端 | CPU、Apple Silicon、量化本地任务；不默认等同于多机数据流水线 |

vLLM与SGLang并非只能做批量任务：同一引擎可同时提供在线服务和离线入口。TensorRT-LLM也不能简单理解成所有路径都必须按同一流程手动编译engine，需看当前后端。

“离线推理”通常表示作业不按用户实时请求逐条响应，不保证首次运行无需网络；模型权重可能仍要下载。与供应商托管Batch API也应区分：后者是服务交付方式，不是本地GPU执行引擎。

## 5. Ray Data与vLLM是什么关系

[Ray Data LLM](https://docs.ray.io/en/latest/data/working-with-llms.html)组织批量数据流水线，可集成vLLM/SGLang等引擎：

```text
Parquet/对象存储
  → Ray Data：读取、分片、预处理、调度GPU actor
  → vLLM/SGLang：执行模型生成
  → Ray Data：后处理、校验、检查点与落盘
```

所以**Ray Data + vLLM**是组合方案，不是在二者之间单纯选一个。Ray Data的行批大小与引擎内部连续批处理、token预算、并发序列数也不是同一参数。

大规模任务要额外设计sample_id、输入/模型版本、幂等写入、失败恢复和完整性对账。框架有checkpoint入口不等于所有外部API副作用天然exactly-once。SQL重变换可能继续放在Spark，模型执行仍交给专用推理工作进程或服务。

## 6. 为什么RL系统里也出现推理框架

RL训练需要反复让当前策略生成样本。以一个示意组合为例：

```text
verl / OpenRLHF：组织训练循环
  ├─ PyTorch + 分布式训练底座：梯度与参数更新
  ├─ vLLM / SGLang：rollout生成
  ├─ 程序验证器 / 奖励模型 / 环境：反馈
  └─ 权重同步与版本管理：让下一轮采样对应合适的策略
```

推理引擎出现在RL里，不表示调用`generate()`就训练了模型。还需要loss、反向传播和优化器更新，以及训练/采样策略版本的一致性管理。异步或允许旧策略样本的方案，也必须控制策略滞后和所需修正，不能任意复用长期旧权重。

模型迁移也不只是文件拷贝：LoRA是否合并、分片格式、tokenizer/chat template、特殊token、量化和采样配置都可能改变结果，切换后先做正确性回归。

## 7. 结合当前学习项目怎么选

1. **继续理解SFT与RL：**保持现有Transformers+TRL，不急于更换分布式框架。
2. **快速完成实际模型SFT：**按定制程度评估LlamaFactory、Axolotl或TRL；资源紧张时核对Unsloth支持路径。
3. **做分布式在线RL/Agent训练：**重点比较verl、OpenRLHF与NeMo RL的模型、算法、硬件、环境接口及恢复能力。
4. **单机批量生成/标注：**先建立vLLM基线，结合前缀/多轮/结构化工作负载比较SGLang；特定NVIDIA部署再评估TensorRT-LLM，支持模型也可测LMDeploy。
5. **海量文档流水线：**评估Ray Data+推理引擎，按数据规模增加多机、恢复与对账；不先把所有数据提交成无界内存列表。
6. **CPU或Mac本地：**先核对llama.cpp等适配路径，不直接复制CUDA训练/推理环境。

没有不带任务条件的“最快框架”。比较同一模型/精度/硬件、输入输出长度、并发、质量、成功率与总成本；长输出、共享前缀、长上下文、MoE、多模态、LoRA都会改变结果。

本次只核对官方能力定位，没有对以上候选做新性能测试。批量与实时服务的更多差异见[既有学习主题](../../202611_批量与实时推理对比/README.md)。
