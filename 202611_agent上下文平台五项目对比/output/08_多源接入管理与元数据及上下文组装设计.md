# 多源接入管理、元数据与按场景组装上下文

原研究与设计2026-11-16；2026-11-17根据会话重建。本报告将用户的重点要求落到平台职责：底层是多种数据服务，需要方便接入、屏蔽结构差异，并管理接入后的技术和业务元数据；在此基础上说明上下文组装与交付。

**需要的是有管理能力的上下文服务平台，包含接入控制面、访问适配、元数据与语义、场景组装、服务交付。五个项目都只覆盖其中部分职责。**以下注册表、页面、状态机和接口为建议设计，不声称已有完整产品实现。

## 1. 管理控制面与运行数据面

假设Agent同时需要数据库交易、HBase行为、CRM REST资料、对象存储合同及内部指标服务。每个Agent自行处理连接、分页、字段、单位和异常，会产生多份不同解释。

| 角色 | 应完成的操作 |
| --- | --- |
| 接入管理员 | 来源注册、连接与secret引用、能力、运行位置、健康与启停 |
| 数据工程师 | 技术Schema到业务模型映射、类型/单位/主键/粒度校验 |
| 业务owner | 术语、指标、判断规则、有效期的审批 |
| 场景配置者 | 选择发布资产，定义依赖、合并、预算和降级 |
| Agent开发者 | 消费授权的业务结构和上下文，不再理解每个源格式 |

屏蔽技术差异时，不能抹掉币种、数据时点、质量、完整性、拒绝/超时/缺失等业务差异。

## 2. 四类接入必须分清

| 类型 | 获取对象 | 代表机制 | 不能推断什么 |
| --- | --- | --- | --- |
| 元数据采集 | 表/列、API schema、owner、血缘、质量 | DataHub/OpenMetadata连接器 | 不等于业务数据运行时代理 |
| 内容同步 | 文档、记录、事件、CDC | 批/增量作业、解析、Semantica ingest | 入库不保证实时 |
| 运行时访问 | 请求对应的业务事实/指标 | SQL/API/HBase适配/Ontop | 执行成功不等于口径正确 |
| 工具公开 | 可由Agent调用的能力 | MCP/Function Calling | 协议不替代前三类建设 |

同一来源可有元数据、内容、运行时多个Binding；共享Source ID，不必共享凭据、作业或刷新周期。

GraphRAG 产物也遵循这一区分：Semantica 可经字段适配消费实体、关系与报告，OpenMetadata 管理其资产、Schema 和血缘；按请求复用检索结果则由服务适配器承担。具体映射、接口依据与权限边界见 [GraphRAG 产物接入说明](../docs/GraphRAG产物接入说明.md)。

## 3. 来源注册与管理对象

```text
Source 来源实例
 ├─ Connection 协议/网络/运行位置/凭据引用
 ├─ ConnectorType 驱动、能力和配置Schema
 └─ Binding 某资产/操作的接入契约
      ├─ PhysicalSchema 源结构与指纹/版本
      ├─ Mapping → CanonicalModel 业务结构
      ├─ AccessPolicy 可信范围
      └─ Run/Checkpoint 任务、调用、水位与错误
```

ConnectorType是可复用插件；Connection是实例；Binding是具体资产/操作，不是一个URL代替全部配置。根据discover_schema、read_records、read_document、query_metric、subscribe_changes等能力开放相应配置，不强迫所有源实现SQL。

### 建议管理界面

| 页面 | 需要的能力 |
| --- | --- |
| 来源中心 | 模板、连接、secret引用、测试、健康、启停 |
| 资产发现 | 预览表/文件/API、选择范围、过滤与排除 |
| 结构映射 | 源Schema对照业务字段，类型/单位/时区/主键/粒度校验 |
| 同步/访问 | 全量、增量、按需；分页、offset、超时、并发、重试 |
| 语义治理 | owner、术语、指标公式、判断规则、有效期、审批 |
| 场景配方 | 依赖DAG、必需/可选、合并规则、预算、降级 |
| 发布运维 | 草稿/测试/发布/回滚、运行记录、影响与失效队列 |

UI建立在统一注册对象和API上，不另维护配置真值。任意代码、复杂SQL及运行环境由工程角色管理，常规操作通过模板和预览完成。

配置状态、来源健康、任务运行状态分别记录。连接成功只说明网络/凭据及部分操作可用，仍需分页完整性、真实权限和业务对照。增量接入需处理重放、幂等、撤回与删除标记。

## 4. 屏蔽结构差异的三层适配

**协议层**处理SQL/JDBC、REST、HBase、文件、消息的调用、编码、分页和异常。Agent不直接指定任意物理连接和凭据。

**结构层**将嵌套JSON、列族cell、表格行映射为受约束Schema，明确可空、类型、精度和数组。字符串元金额按批准规则转整数分；缺字段和null区分，不默默猜字段或补零。

**语义层**确定customer_no/accountId是否同一实体，amount是订单额还是净回款；明确权威来源、关联主键、基数、去重和冲突策略。同一订单从三个通道读到，是备选访问或副本，不是三份收入。

### 多种payload，共同外层契约

| 类型 | 内容 | 特有契约 |
| --- | --- | --- |
| recordset | 记录、指标结果 | Schema、粒度、单位、分页、完整性 |
| document | 政策、合同 | 原文span/页、有效期、版本 |
| graph | 实体和关系 | URI、本体版本、关系语义、来源 |
| event_batch | 事件/CDC | event ID、offset、水位、删除/重放 |

共同外层包含source/binding/asset ID、Schema/映射版本、数据时间、授权范围、质量、状态与来源引用。统一契约不意味着都转成字符串；大结果提供受控artifact引用和分页，避免塞进模型窗口。

## 5. 元数据分六类管理

| 类别 | 内容 | 维护责任 |
| --- | --- | --- |
| 技术 | 表/字段/API请求响应Schema、键、类型、编码 | 连接器发现，工程审核破坏性变更 |
| 运行 | 同步时间、水位、行数、任务/接口状态、延迟 | 作业和服务自动回写 |
| 业务 | 实体、术语、公式、判断规则、粒度、单位 | owner批准，工程绑定执行表达式 |
| 治理 | owner、敏感、权限、范围、保留期限 | 治理与资产负责人 |
| 来源派生 | 字段血缘、原文→抽取→摘要、查询→结果→答案 | 按实际运行事件捕获 |
| 场景 | 配方、依赖、必需项、预算、降级、评估与版本 | 场景owner与工程 |

目录提供可发现视图，secret明文留在凭据系统，offset放作业存储；业务模型和配方可在Git管理，通过ID/版本关联。避免多个系统重复维护同一公式。

链路应当是：源字段→技术Schema→业务实体/字段→批准指标/规则→场景配方→结果证据。OpenAPI只定义结构，不自动说明业务口径；RDF概念也不自动提供金额单位。

## 6. Schema和语义变更闭环

发现变更先生成候选revision，与发布版比较。新增可选字段、删除字段、类型变化、单位变化分别处理；同名字段由元改成分也是破坏性语义变化。

列出影响的Mapping、指标、索引、缓存和配方；不兼容Binding隔离或拒绝相应请求。测试、批准、发布后再切流量，并撤回旧派生上下文。来源disabled不自动表示历史数据已经删除，任务失败也不等于配置永久失效。

## 7. 场景组装不只是top-K拼接

例如“解释某客户本月回款异常”，配方声明：

| 依赖 | 用途 | 规则 |
| --- | --- | --- |
| 批准指标定义 | 固定口径 | 必需、版本匹配 |
| 客户/组织映射 | 统一身份与权限 | 必需、可信ID |
| 交易聚合/分项 | 精确数值 | 必需、批准执行Binding |
| 生效政策 | 规则解释 | 对该解释必需、有效期/来源检查 |
| 工单/备注 | 补充可能原因 | 可选，不能直接归因为因果 |

以可信身份确定范围，绑定配方和语义版本，再建立依赖DAG：独立任务可并行，需客户ID的节点等待。只在已批准且语义等价的Binding间回退，不能自动更换另一种口径。

组装前校验结构、单位、完整性、数据时点、质量、权限和依赖版本。按显式规则合并实体和去重，数字按受控计算，文本按相关性和来源选择，最后分配预算与渲染。

### 缺失与失败

必需指标失败、无批准口径或无权限时阻断相关结论；可选工单失败可以partial并说明范围；只有成功且完整执行后无数据才是empty。旧规则撤回后排除证据，若它是必需项则失败。不把异常转换成0或“没有问题”。

### 预算和复现

先为口径、数值与引用预留预算，再放可选材料。使用真实模型tokenizer，字符数只作粗筛；大表返回摘要和受控引用。记录配方、Binding、Schema、映射、数据水位、授权、源文档、索引和模型版本；多系统无全局快照时明确时间差。

## 8. 五项目重新评估

| 项目 | 接入管理 | 实际业务结构适配 | 元数据与语义 | 场景组装 |
| --- | --- | --- | --- | --- |
| DataHub | 元数据来源UI/调度/secret/记录 | aspect统一非记录代理 | 强项 | 工具提供发现，完整配方外接 |
| OpenMetadata | Service/采集工作流，含API资产Schema | 目录Schema非运行代理 | 强项；许可与商业界面有边界 | MCP/SDK访问，业务编排外接 |
| Semantica | ingest代码扩展，未证实完整后台 | 解析/归一可参考，业务模型另定 | 知识/来源重点 | 检索/grounded/失效可参考 |
| Ontop | 连接/映射，非通用门户 | 支持范围SQL→RDF | 本体与映射 | 查询分支，外围场景服务 |
| GraphRAG | 配置/reader/程序接口 | documents统一 | 文档/索引元数据 | 文档检索分支 |

五者没有被本次证据证明能独立满足整个闭环。以界面和治理为优先时先选目录底座，以运行时访问为优先时单列数据访问层。

## 9. 补缺选项和交付方式

优先复用既有网关/数据集成/作业/查询平台。需要时专项评估Trino的SQL联邦与类型映射、Camel的API/消息路由与转换、NiFi的可视化采集与record转换。这些是额外候选，不是已包含在五项目中的功能，本次未部署或做其源码深度对比。

ContextBundle可经同步HTTP/SDK提供，也可作为MCP工具返回；长作业用job ID和状态查询，大结果用带权限/有效期的artifact引用，流式事件保留序号与完成标记。协议只是交付方式，不能改变内容类型和授权语义。

## 10. 本次原型与验收

[多源原型](../scripts/source_management_demo.py)用虚构SQL行、REST嵌套JSON和类HBase cells，适配为同一业务模型；选择一个权威通道，正确结果250元，错误累加三个副本为750元。

这是离线代码原型，没有管理界面、真实HBase/REST调用或框架服务。真实PoC要验证新增来源是否需改Agent、管理员能否测试预览发布、Schema/单位漂移能否阻断、分页是否完整、增量是否幂等、权限和撤回是否传播到派生上下文。
