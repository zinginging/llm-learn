# 从三项目调研走向业务 POC

本文是实验设计，不是已完成的业务测评。2026-11-09 的本地验证只覆盖源码接口静态核对和离线教学计算。

## 1. 先明确到底缺什么能力

| 业务症状 | 优先验证方向 | 可能更简单的修复 |
| --- | --- | --- |
| 回答只覆盖少数文档，漏掉全局主题 | GraphRAG Global；与文本分层摘要基线比较 | 建立分类、摘要与分面检索 |
| 具体对象和跨对象关系经常分开 | LightRAG local/hybrid/mix | 查询改写、BM25+向量融合、重排 |
| 桥接文档难召回，必须跨多篇证据 | HippoRAG 2；GraphRAG Local/DRIFT 也作为候选 | 多轮检索或显式子问题分解 |
| PDF 表格、扫描件解析错误 | 三者都先暂停算法升级 | 修复 OCR、表格抽取、章节边界 |
| 财务金额、订单总量不准确 | 结构化查询与语义层 | 数据模型、指标口径、SQL 校验 |
| 旧资料、权限混用 | 所有组件都要额外治理 | 有效期、租户、ACL、血缘、撤回机制 |

“能调用 API”只是接通；“答得像人”不代表证据正确；“支持插件后端”不等于可满足吞吐、事务与容灾要求。

## 2. 用什么基线与数据

至少保留两条基线：BM25+向量融合+重排，以及不使用图的相同生成链路。若目标是全局综述，另加入对原文/章节做分层摘要再汇总的基线，避免把“提前摘要的收益”全部归给图。

教学用的[11 篇虚构短文](../input/企业知识样例.json)只适合查流程错误；业务 POC 可先选数百至数千份代表性资料和一批人工审定问题，再按语料规模扩展。样本规模由数据类型、错误成本和可标注资源确定，不用教学集的满分作为上线依据。

问题按单跳事实、多跳关联、别名与歧义、全局综述、时间变化、无答案、权限隔离分组。对同一对象的改写和近重复问题不能随机打散到调参集与测试集，否则会高估泛化；按对象、资料来源或时间切分，保留冻结测试集。

每题不仅标答案，还标最小支持文档集合、有效时间、关键否定/限制、禁止使用的资料，以及能否回答。全局综述标应覆盖的主题与代表性原文；不能只标一段可能措辞不同的参考答案。

## 3. 公平比较如何配置

| 对齐项 | 处理方法 |
| --- | --- |
| 原始数据 | 同一解析和清洗版本、来源 ID、时间、权限；记录每次快照 |
| 模型 | 尽量同一抽取、embedding、回答模型；不支持同一模型的差异单列 |
| 切块 | 先统一基线；再给各算法合理调优预算，分别报告，避免只强行统一 |
| 模式 | 按任务预先路由；比较 GraphRAG Global 与 LightRAG global 时明确算法不同 |
| 上下文 | 对齐实际进入回答模型的 token 预算，另记图/报告/筛选调用 |
| 生成 | 相同回答要求与来源要求；控制温度、最大输出、答案格式 |
| 成本 | 完整记录建库、更新、查询、embedding、重排和重试；保存 usage |
| 运行 | 记录硬件、依赖锁、并发、缓存冷热、限流与失败；不混合冷启动/热缓存 |

可以报告“统一配置比较”和“同等调优预算的最佳配置比较”两组结果。某方法的默认 top-k 不是另一个方法的公平默认。

## 4. 不只看一个准确率

设第 i 题金标准支持文档集合为 Gi，前 k 个召回文档映射为 Ri,k。对有支持文档的题：

\[
Recall_i@k=\frac{|G_i\cap R_{i,k}|}{|G_i|}
\]

若需要三篇原文而只召回两篇，recall=2/3，仍可能无法得出完整结论。因此再报告 **all-evidence@k**：全部必要证据是否都在前 k 个中。这是本方案的业务验收指标名称，不宣称三论文都使用此指标。

无答案题的 Gi 为空，不能用上式除以零或把 recall 自动记为 1；单独统计拒答、误答和支持不足时编造的情况。候选图实体、关系与社区报告，应通过来源映射到原文后再统计；一份大摘要引用了整个库，不等于实际精确召回全库证据。

| 层次 | 指标或检查 | 说明 |
| --- | --- | --- |
| 数据 | 解析正确、来源完整、重复率、过期标记 | 数据问题与检索问题分开归因 |
| 检索 | recall@k、all-evidence@k、相关性/排序 | 多跳题重点看桥接证据，别只看最终答案 |
| 事实答案 | 业务精确匹配或人工语义正确性，按类型分组 | 中文 token F1 需预先定义分词；不能直接照搬英语评分 |
| 引用 | 是否支持具体声明、引用覆盖与时效 | “引用了一个真实文档”不等于引用正确 |
| 全局综述 | 主题覆盖、事实支持、冗余、遗漏 | LLM judge 辅助，交换答案顺序并人工抽查 |
| 无答案与冲突 | 拒答质量、错误确定性、过期事实使用率 | 正确回答范围与时态需明确 |
| 工程 | 建库时长与费用，p50/p95 延迟、吞吐、失败率 | 分阶段记录，含在线筛选及重排 |
| 更新 | 新增可见延迟、删除残留、重启一致性 | 有功能入口不等于有可靠 SLA |

得分区间和改进幅度应考虑样本量，使用适合任务的 bootstrap 等不确定性估计；不存在通用的“95% 就能上线”。阈值由业务错误成本在验证集上确定，最终只在冻结测试集评估一次。

## 5. 更新、删除、权限要单独测

按顺序建立初始索引，再新增文档、更改事实、删除资料、重启服务、重新查询。至少包括：

1. 一个实体有多份来源；删去其中一份后保留其余合法证据，但不能保留已撤回的独有事实。
2. 负责人变更；历史问题保留历史答案，当前问题采用新事实，不能混淆时点。
3. 相似名字并不代表同一实体；同义连接和归并不能跨错对象。
4. 写入失败后重试；避免图已写但向量未写、状态错误或重复边无法恢复。
5. 两个权限域共享同名机构；低权限查询不能通过实体描述、社区报告、重排或缓存看到受限资料。
6. 删除后不仅问原问题，还用别名和改写查询，并在进程重启后再检查。

派生摘要按原始来源的权限和有效期治理。查询前过滤、图扩展中的过滤与汇总时的过滤需一致；只在最终文本脱敏不能修复混合摘要泄漏。

## 6. 成本和服务设计

把总链路拆为 parsing、OpenIE/抽取、embedding、图构建/摘要、query preprocessing、retrieval、recognition/rerank、answer。每段记录 wall time、调用数、输入输出 token、缓存命中、错误和重试。

异步并发可缩短建库时间，但受 API 限流、数据库写能力和存储一致性约束。批量模型接口可降低离线加工成本，但依赖链、失败恢复与完成延迟要协调；在线查询不要照搬离线 batch SLA。

GraphRAG 重点观察社区报告和 map/reduce；LightRAG 重点观察实体关系抽取、关键词和多存储写入；HippoRAG 2 重点观察 OpenIE、事实向量、recognition 与图准备。对任何一方，最终回答的 token 只是总成本的一部分。

索引版本、模型/向量身份、来源版本和权限策略应一起发布。升级时先生成新索引，回放冻结问题和删除权限测试，再切流；不要在旧索引上随意替换 embedding。

## 7. 如何给出选型结论

用分组结果说明取舍，例如“某类多跳问题全部证据召回提高，但建库成本和在线 p95 增加；全局总结仍走另一条链路”。如果混合路由优于单一组件，可以按问题类型组合，但应把分类错误和多索引维护成本计入。

本次调研的初始建议是：全局分析先试 GraphRAG，工程化知识库先试 LightRAG，关联原文检索先试 HippoRAG 2；简单问题始终保留普通混合检索。最终决策依据为统一业务 POC，不使用跨论文表格直接排名。
