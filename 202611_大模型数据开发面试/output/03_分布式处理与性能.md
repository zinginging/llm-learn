# 03 分布式处理与性能

本章问题来自候选人自述及扩展编码题，原始定位见[采集记录](../docs/问题采集与分类.md)。回答不能照搬面经里的口头解释；以下按官方机制重建。

<a id="q13"></a>
## Q13 Spark宽窄依赖、shuffle、惰性执行和action是什么关系？

**先答结论：**依赖描述分区之间的数据关系；shuffle是跨分区重新分布数据；惰性执行是先构建计算计划；action通常触发作业。四者有关联，但不是同义词。

RDD窄依赖中，一个父分区的数据只被有限的特定子分区使用，可在同一stage内流水执行，例如map/filter。宽依赖通常要求多个父分区的数据汇聚到子分区，引入shuffle边界，如按新key聚合或重分区。DataFrame应结合优化后的物理计划判断，不能看到join就断言一定发生shuffle；广播join、已有分布和优化规则会改变执行。

shuffle可能涉及序列化、网络、排序、磁盘spill和fetch，代价不只是网络传输。count、collect、show等会触发计算；sum/groupBy等在不同API中可能只是构造表达式或转换，不能把SQL聚合函数名单直接背成全部是action。

**例子：**过滤无效语料→提取fingerprint可在分区内执行；按fingerprint聚合形成跨分区交换；写出结果触发整条链路。应看`explain`和Spark UI，核对stage、exchange、数据量及任务分布。

**追问与误区：**cache不是立即执行所有计算，通常在后续action才物化；lineage支持重算，不等于所有外部副作用都能自动回滚。减少shuffle也要保留正确性，例如不能为“优化”随意丢弃跨分区重复数据。

题源：I01。依据：[T03、T04](../docs/答案依据与研究笔记.md)。

<a id="q14"></a>
## Q14 Spark数据倾斜怎么定位和处理？加盐有什么限制？

**先答结论：**先证明少数分区或key承担异常负载，再选针对性方案；运行慢不必然是倾斜。看task时长分布、shuffle bytes、输入记录、spill、GC与热点key频次。

按成因处理：join中可广播确实足够小且安全的表、利用AQE可支持的skew处理、隔离热点key、调整分区与预聚合；聚合中可先局部聚合再全局归并。NULL或“未知”占比很高时，应按业务语义处理，不能为了均衡把这些记录全部删掉。

加盐把热点key拆成(key,salt)以分散计算。聚合完成后必须去掉salt再汇总；join时另一侧需要匹配正确的salt展开策略，避免漏配或重复。对于去重和非可加指标，要证明两阶段合并仍保留语义。

**例子：**求平均值时分桶先保留sum和count，最终用总sum/总count；直接平均每桶平均值会在桶大小不同的情况下出错。求全局近重复簇也不能把各桶独立结果简单union后就宣布全局完成。

**追问与误区：**增加executor数量不一定拆开一个巨大的热点分区。广播一个估计错误的“大表”可能让每个executor都OOM。盐值生成应可重复，且日志应记录策略版本，避免重跑改变数据结果和分片身份。

题源：I01。依据：[T03、T04](../docs/答案依据与研究笔记.md)。

<a id="q15"></a>
## Q15 Spark任务OOM或失败，如何系统排查？

**先答结论：**先确定失败位置、内存类型和数据阶段，再调整资源。driver、executor JVM、Python worker、原生/Arrow和容器总内存是不同边界。

先看失败task和日志：driver是否collect了全量结果；executor是否遇到大分区、巨型group或广播表；Python是否每行创建大量对象或重复加载模型；容器是否因为非JVM开销超过限制被杀。结合stage输入、shuffle、峰值内存、spill、GC时间与重试模式，区分确定性坏数据、资源耗尽和临时网络错误。

修复顺序通常是减少不必要数据、列裁剪与过滤→控制分区/批次和热点→避免过大分组及无界collect→治理UDF对象与模型生命周期→按证据调内存、overhead与并发。内存加大可能缓解，也可能只把失败推迟，甚至增加GC或减少可用并行度。

**例子：**一组用户拥有千万条记录，grouped pandas UDF可能将整个组放进内存；把全表分区数翻倍仍不能拆开这一个组，应改算法或显式分解，再证明合并语义。

**追问与误区：**重试前确认写入是否幂等，否则计算恢复可能产生重复输出。持续executor lost还要看磁盘满、shuffle fetch失败、抢占和网络，不要把所有异常都归因于“内存不够”。保存最小坏样本与运行配置，避免只记最后一次成功参数。

题源：I01。依据：[T03–T05](../docs/答案依据与研究笔记.md)。

<a id="q16"></a>
## Q16 PySpark为什么有时慢于Java/Scala？如何优化？

**先答结论：**要分清原生DataFrame表达式、Python RDD函数、普通Python UDF和pandas/Arrow UDF。用PySpark不意味着每一行都在Python和JVM之间来回传。

`select/filter/join`等内置表达式通常生成由Spark引擎执行的计划，与调用语言不同不是同一个层次的问题。性能差距常来自跨语言序列化、Python逐行执行、优化器无法理解的自定义逻辑、批次开销和重复对象拷贝。Java/Scala代码写法不好也可能慢。

优先使用内置SQL函数与列运算；确需UDF时评估向量化和Arrow，设置合适批次，复用模型/连接，避免每行初始化。先比对物理计划、相同数据和资源、冷热缓存，再拆解CPU、序列化与I/O耗时，不能仅按语言下结论。

**例子：**把字符串小写用内置`lower`而非Python UDF；但复杂领域解析可能仍需要Python，这时应批量调用并控制对象大小。Arrow减少某些转换开销，不消除全部Python执行，也不保证总耗时下降。

**追问与误区：**不要逐条写远程API的UDF然后期待Spark自动保证配额、幂等和账单；推理步骤应有任务身份、批次、限流、缓存、失败队列与结果校验。使用模型推理前核对进程数×模型副本是否超过内存。

题源：I01，原帖中的简化解释未作为答案依据。依据：[T04、T05](../docs/答案依据与研究笔记.md)。

## Q17 Ray是什么，与Spark在数据加工中如何分工？

**先答结论：**Ray提供分布式任务与actor等执行抽象，Ray Data面向可扩展数据处理及AI批量推理；Spark在结构化SQL、join、聚合和数据平台生态中成熟。应按计算形态与团队能力选，不是“新框架取代旧框架”。

大表join、复杂SQL和稳定的湖仓作业可优先复用Spark；逐文档解析、批量embedding、需要长期驻留模型的GPU推理，可以评估Ray Data的批处理与actor执行。二者都能覆盖部分对方任务，最终看实际吞吐、资源利用、容错、连接器和运维成本。

Ray actor可让模型在工作进程中复用，减少反复加载；但模型副本、batch size、对象存储、背压和CPU/GPU配额仍要调。Spark也能组织推理，不能把GPU能力描述成Ray独有。跨框架搬运中间数据和恢复协议可能抵消计算收益。

**例子：**Spark对网页元数据做准入、去重和分区发布；Ray从已固定清单读取文档做OCR/embedding；两侧按sample_id、规则版本和输出契约对账。也可全部采用同一框架，避免没有收益的异构复杂度。

**追问与误区：**actor崩溃重建后外部调用是否会重复？返回的向量是否完整且属于同一模型版本？这些比“用了Ray所以更快”更能体现数据工程能力。本次未运行Ray/Spark性能对比。

题源：I01的Ray问题，框架比较为研究追问。依据：[T04、T06](../docs/答案依据与研究笔记.md)。

## Q18 用SQL对变更事件去重并保留最新值，如何做到确定性与幂等？

**先答结论：**定义业务键与可信事件顺序，以稳定排序选最新，保留删除墓碑，并确保重放旧事件不会覆盖新状态。只有event_time通常不够。

假设单一有序源为每个业务键提供单调递增的version，排序用version，再用明确的事件序号处理约定内的并列。不同payload却有相同版本属于冲突，必须报警或按来源优先级仲裁，不能把随机ID的字典序当成业务真相。

```sql
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY entity_id ORDER BY source_version DESC
  ) AS rn
  FROM changes
)
SELECT * FROM ranked WHERE rn = 1;
```

这是批次内部去重。合并目标表时还要比较目标已有版本，只接受更新的事件；同版本相同内容应no-op，同版本不同内容应进入冲突队列。删除事件也要保留版本：若直接移除目标行，迟到旧插入可能把已经删除的数据复活。读业务结果时过滤墓碑，而不是丢弃版本状态。

**例子与验证：**[实验脚本](../scripts/interview_exercises.py)重放同一批、乱序追加旧事件、再删除，检查目标保持最新且不复活。实际CDC还要处理分区迁移、事务边界和多源合并，不能把教学version简化推广为所有系统都有全局序列。

题源：研究扩展编码题，源于DE-cdc幂等主题。依据：[T09、T24](../docs/答案依据与研究笔记.md)。
